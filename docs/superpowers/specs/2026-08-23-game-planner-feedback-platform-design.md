# AgentFlow 游戏策划/运营 AI 流程平台设计

## 1. 背景与目标

AgentFlow 面向游戏策划、运营和用户研究人员，解决其搭建 AI 流程时的两类核心问题：

- **复用难**：一次性的提示词、表格和人工处理经验无法沉淀为可配置、可复制、可版本化的流程。
- **不可观测**：AI 输出为何产生、在哪个节点失败、成本如何、人工是否采纳、版本改动是否有效均不可追踪。

本次改造保留现有 React Flow、FastAPI、DAG 执行、SSE 与节点日志底座，重构产品语言、示例数据和页面结构，使平台成为面向策划/运营的可视化零代码 AI 流程编排平台。

唯一完整演示场景为“玩家反馈自动分流”，串联策划用研的 `收集 -> 分类 -> 分发 -> 验证` 闭环。战斗策划、数值策划和系统策划是重点接收角色，但产品不收窄为单一战斗数值工具。

### 成功标准

1. 面试演示可在无外部 API 凭证的 Mock 模式下稳定跑通完整闭环。
2. 用户可选择内置示例或导入 CSV，创建一批玩家反馈并启动流程。
3. 每条反馈的分类、优先级、去向、置信度和证据片段可追溯到具体流程运行与节点日志。
4. 策划可修正 AI 结论、记录处理决策和版本验证结果。
5. 模板可复制、配置可编辑、发布版本不可变，证明流程可以复用。

## 2. 用户与任务

| 用户 | 核心任务 | 所需决策 |
| --- | --- | --- |
| 战斗策划 | 判断角色、技能、关卡和战斗节奏问题 | 是否改机制，改什么，如何验证 |
| 数值策划 | 判断胜率、伤害、养成和资源问题 | 优先级、数值调整范围、风险 |
| 系统策划 | 判断匹配、段位、活动规则和入口体验 | 是否进入需求池与责任边界 |
| 运营/用研 | 汇集渠道反馈、发现趋势、推动处理 | 哪类问题上升、交由谁处理 |
| 研发/客服 | 接收明确的缺陷或个案任务 | 是否为缺陷、如何跟进或回复 |

主任务不是让 AI “自动回复玩家”，而是将非结构化玩家文本转化为可被策划讨论、执行和验证的结构化问题。

## 3. 竞品拆解与产品机会

| 竞品类别 | 代表能力 | 缺口 | AgentFlow 的取舍 |
| --- | --- | --- | --- |
| 通用零代码 AI 编排平台 | 连接器丰富、流程搭建灵活 | 缺少游戏版本、对象、策划决策和验证语义 | 用通用 DAG 作为底座，提供游戏反馈模板与策划字段 |
| 客服/工单自动化平台 | 工单收集、标签、分派成熟 | 以服务闭环为主，无法解释平衡性、体验和版本风险 | 复用其批次与路由价值，补足优先级解释与版本验证 |
| 游戏数据/反馈分析工具 | 看板、数据切片、玩家洞察 | 多为分析终点，难以把 AI 判断变成可复用且可观测的执行流程 | 把分析指标连接到流程、人工校验和验证回写 |

产品机会是：不与通用编排平台比连接器数量，而是将“反馈洞察到版本决策”的方法沉淀为模板，且用业务质量指标证明 AI 流程是否真正有效。

## 4. 产品范围

### 4.1 本期包含

- 决策总览、反馈批次、流程编排、运行监控、验证复盘和模板中心。
- 内置“竞技场版本反馈”示例批次；CSV 轻量导入。
- “玩家反馈自动分流”可复用模板、草稿、复制与不可变发布版本。
- 分类、优先级、团队路由、人工复核和版本验证节点/数据语义。
- 实时节点状态、输入输出、耗时、Token、成本、错误和重试观察。
- Mock LLM 稳定演示，以及既有 OpenAI-compatible 网关能力。

### 4.2 本期不包含

- 真实工单、IM、埋点或数据仓库连接器。
- CSV 列映射向导、异步大文件处理和数据清洗平台。
- 多人实时协作、权限审批、外部任务系统回写。
- 自动化数值模拟、实战日志计算、真实胜率归因。

## 5. 信息架构与关键页面

| 页面 | 目的 | 核心内容与动作 |
| --- | --- | --- |
| 决策总览 | 让策划快速识别版本风险 | P0/P1 问题、战斗风险、反馈趋势、待验证改动、流程质量指标 |
| 反馈批次 | 管理输入与样本质量 | 选择示例、上传 CSV、查看字段校验和批次状态 |
| 流程编排 | 沉淀可复用的 AI 工作方法 | 模板选择、React Flow 画布、节点配置、保存、发布、试运行 |
| 运行监控 | 回答“流程是否正常工作” | 节点状态、日志、耗时、Token、成本、重试与错误 |
| 分流结果 | 回答“每条反馈如何处理” | 分类、证据、置信度、优先级、接收角色、人工修正 |
| 验证复盘 | 回答“决策是否有效” | 采纳/驳回、版本号、调整方案、目标指标、验证结论 |
| 模板中心 | 解决复用问题 | 模板说明、输入字段、节点配置、使用次数、复制创建 |

## 6. 玩家反馈自动分流流程

### 6.1 收集

输入由内置示例或 CSV 产生反馈批次。MVP CSV 固定接受如下字段：

`feedback_id`、`version`、`region`、`channel`、`player_text`、`reported_count`、`affected_players`。

内置示例额外携带可展示的游戏上下文，例如模式、段位、英雄/角色、关卡和战斗局数。导入时做必填字段和行级错误校验；无效行不进入执行，返回可下载/查看的错误摘要。

### 6.2 分类

AI 将玩家文本输出为结构化结果：

- `category`：战斗机制、角色平衡、关卡体验、数值经济、系统体验、研发缺陷、非有效反馈。
- `game_objects`：角色、技能、装备、关卡、模式或系统对象。
- `sentiment`：正向、中性、负向。
- `severity`：P0 至 P3 所需的严重度因子。
- `confidence`：0-1 的模型置信度。
- `evidence`：支持判断的原文片段。

典型战斗语义包括技能手感、控制链、前后摇、目标选择、角色胜率、Ban/Pick、伤害倍率、克制关系、Boss 难度和失败节点。

### 6.3 分发

优先级由可解释规则计算：

`priority_score = severity * 0.4 + frequency * 0.3 + affected_scope * 0.2 + version_goal_relevance * 0.1`

输出分数、每个因子和最终 P0-P3 标签。路由规则如下：

| 信号 | 默认接收角色 |
| --- | --- |
| 技能机制、战斗节奏、角色克制、关卡体验 | 战斗策划 |
| 胜率、伤害、养成、装备、资源产出 | 数值策划 |
| 匹配、段位、活动和系统规则 | 系统策划 |
| 配置、表现与功能异常 | 研发 |
| 个案处理、补偿与解释 | 客服 |
| 置信度低于阈值或规则冲突 | 人工复核池 |

### 6.4 验证

策划可修正分类、优先级和接收方，选择采纳、驳回或待验证，并填写调整方案、目标版本与验证指标。

战斗改动的示例为：“冰霜法师二技能控制时长 1.8 秒调整为 1.2 秒”；验证目标为目标段位胜率回归 48%-52%、Ban 率下降、相关负面反馈率下降且平均对局时长不显著恶化。结果标为生效、继续观察或回滚，并回写流程质量指标。

## 7. 可复用与可观测设计

### 7.1 复用

模板包含图结构、节点配置、CSV 输入字段约定、优先级权重、路由规则、人工复核阈值和版本说明。用户从模板复制为草稿修改，发布时生成不可变快照；后续执行绑定发布版本，保证复盘可复现。

首批模板：

1. 玩家反馈自动分流（主 Demo）。
2. 版本上线 72 小时平衡性预警。
3. 新系统体验回收与需求归并。

### 7.2 可观测

平台区分两层指标，避免把“接口成功”误作“业务有效”。

| 维度 | 指标 |
| --- | --- |
| 运行可靠性 | 执行成功率、节点耗时、重试次数、错误类型、Token、成本 |
| AI 判断质量 | 置信度分布、人工复核率、人工修正率、分类/分发准确率 |
| 业务结果 | P0/P1 发现量、平均分流时长、采纳率、版本后同类反馈变化、验证完成率 |

节点日志展示输入摘要、输出摘要、模型/规则版本、耗时、Token、错误和重试。分流结果页展示证据片段和优先级分解，保证策划能解释和修正结论。

## 8. 技术设计

### 8.1 前端

保留 React、TypeScript、Vite、React Flow、Recharts 与 Lucide。将现有通用导航改为策划语义，并在流程编辑器中扩展下列节点配置：

- `feedback_batch`：选择内置数据或导入结果。
- `agent`：分类 schema、提示词和置信度阈值。
- `priority`：评分权重及版本目标相关性。
- `route`：问题类型到责任角色的映射。
- `human_review`：复核队列和人工结论。
- `verification`：版本、调整方案、指标和结论。

MVP 可将部分节点映射到现有 agent/condition/notification/output 执行类型，但前端显示业务名称，后端以配置区分行为。

### 8.2 后端

保留 FastAPI、SQLAlchemy、DAG engine、SSE、SQLite/PostgreSQL 兼容存储和 Mock/真实 LLM 网关。新增领域实体或 JSON 配置：

- `FeedbackBatch`：批次元数据、来源、字段校验结果和统计。
- `PlayerFeedback`：原始文本、游戏上下文、结构化分类与分流状态。
- `FeedbackDecision`：人工修正、优先级、接收角色、采纳状态。
- `VerificationRecord`：目标版本、调整方案、指标、结论与备注。

执行引擎为批次反馈逐条执行并关联 `Execution`/`ExecutionLog`。演示数据量控制在几十条，保持 BackgroundTask 与 SSE 体验稳定；未来大批量任务才迁移到 Celery 队列。

### 8.3 API 边界

- `POST /feedback-batches/demo`：创建内置示例批次。
- `POST /feedback-batches/import`：上传并校验 CSV。
- `GET /feedback-batches`、`GET /feedback-batches/{id}`：批次与统计。
- `GET /feedbacks`、`PATCH /feedbacks/{id}/decision`：结果查询与人工修正。
- `POST /feedbacks/{id}/verification`：创建或更新验证记录。
- 现有 workflow/template/execution/analytics 接口保留，扩充策划指标字段。

## 9. 异常处理与边界

- CSV 缺字段、空文本、错误编码或超限行数：返回行级错误，不创建可执行批次。
- LLM 返回非法 JSON、超时或瞬时故障：沿用分级重试并记录失败节点；最终失败反馈进入人工池，不丢失原文。
- 低置信度、多个规则冲突、缺少游戏对象：不自动路由到业务团队，进入人工复核。
- 已发布流程不能编辑；复制后创建草稿，避免历史执行被配置变更污染。
- 验证记录缺少版本或结论时保持待验证，不计入有效性指标。

## 10. 测试与演示

后端单测覆盖 CSV 校验、优先级计算、路由规则、低置信度人工池、人工修正和验证回写；保留图校验、分支终点和 LLM 重试测试。API 测试覆盖示例批次创建、执行、结果查询与修正。前端至少验证构建、模板到流程、试运行、SSE 节点状态和结果页关键状态。

面试演示顺序：

1. 从决策总览说明本版本的战斗/数值风险和待验证改动。
2. 打开模板中心，说明如何沉淀“玩家反馈自动分流”流程以解决复用难。
3. 选择内置竞技场反馈批次或导入 CSV，在画布上说明分类、优先级和路由规则。
4. 试运行流程，打开实时运行监控解释节点日志、成本和失败定位。
5. 查看一条角色平衡反馈的证据、评分和战斗/数值策划去向。
6. 人工修正一条低置信度结果，记录版本调整和验证目标。
7. 在验证复盘展示版本后反馈变化，说明 AI 的价值需以决策效果而非调用成功率衡量。

## 11. 简历与项目表述

“针对策划/运营搭建 AI 流程时复用难、不可观测的痛点，完成竞品拆解与 PRD；以 FastAPI + React/React Flow 落地可视化零代码编排平台。以玩家反馈自动分流为示范，串联收集、分类、分发、验证闭环，并通过流程模板、节点级日志、人工复核与版本指标回写，支持战斗/数值/系统策划的版本决策。”
