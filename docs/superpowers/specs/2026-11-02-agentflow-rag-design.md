# AgentFlow：证据驱动售后 Agent 改进设计稿

日期：2026-11-02。状态：待评审，未实现。面向 Agent 应用开发 / AI 全栈实习作品集。

## 1. 本轮目标与范围

将已有售后工作台升级为能够检索租户政策、引用有效条款、处理多轮补充并安全提交工单的应用。核心演示：用户询问订单退款条件，Agent 查询订单与政策，说明适用条件，生成待审核草稿；政策在审核前更新时，系统拒绝旧草稿并要求重新核对。

本轮交付范围为政策检索、可核查引用、索引生命周期、评测和现有工作台的检索状态展示。订单查询、审批、调度和租约沿用现有实现。仍只创建平台内工单，不声称真实退款或接入企业订单系统。

本轮不加入多 Agent、知识图谱、模型训练、PDF/OCR、跨会话长期记忆或任意工具代码执行。文字逐 Token 推送作为后续独立改造，当前优先显示真实执行事件。

## 3. 技术方案选择

| 方案 | 优点 | 代价 | 决策 |
|---|---|---|---|
| 词法 + 本地 embedding + 精确余弦检索 | 保留 SQLite 开发方式，便于逐条核对结果 | 数据规模有限，需测量内存与耗时 | 第一阶段采用 |
| PostgreSQL + pgvector | 可在现有 PostgreSQL 内管理向量与过滤 | 数据库扩展、容器及迁移增加工作量 | 第二阶段性能验证后引入 |
| 独立向量数据库 | 可独立扩容 | 增加服务、租户过滤和双写一致性成本 | 当前不采用 |

第一阶段限制每个租户有效政策总计最多 2000 块；超限导入返回明确错误，不静默截断。该数值是初始工程上限，不是性能承诺。准备 200、1000、2000 块规模测试，记录 CPU、内存和检索 p50/p95 后调整。

Embedding 首选候选为 `BAAI/bge-small-zh-v1.5`，独立 CPU 推理，避免与本地生成模型争用 8GB 显存。实现阶段固定模型 revision、维度、归一化方式及查询指令；更换任一项产生新索引版本。生成模型与 embedding 模型分开配置，不能用 Qwen 聊天输出代替向量。

依据：[BGE 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[pgvector 官方仓库](https://github.com/pgvector/pgvector)。具体依赖锁定及安装验证属于实施阶段，本稿不承诺尚未测量的效果。

## 4. 数据与索引生命周期

新增独立模块 `retrieval/`：chunking、embeddings、indexing、ranking、schemas，避免继续扩大业务执行器。

新增逻辑实体（实施时按现有 SQLAlchemy 约定命名）：

- PolicyChunk：tenant_id、policy_id、policy_version、chunk_id、正文、标题路径、段落/字符位置、正文哈希、chunker_version。
- PolicyIndex：tenant_id、policy_id、embedding_revision、chunker_version、index_generation、状态、错误码、租约/重试次数、创建及完成时间。
- ChunkEmbedding：chunk_id、index_generation、model_revision、维度、归一化向量。第一版可用数据库 JSON 存储，由适配器隐藏底层实现。
- RetrievalTrace：run_id、tool_call_id、snapshot_id、检索方式、候选块 ID/排名、最终引用、耗时、降级原因、重查次数。

索引状态：pending → running → ready / failed。资料导入先持久化政策及索引任务；请求接口不等待 embedding。后台任务以租户、政策、正文哈希、模型及分块版本组成幂等键；唯一约束防重复结果。分批生成过程中不能发布半份索引，完整校验后事务切换 ready。

分块先保留标题、段落、条款序号，再按 embedding tokenizer 上限拆分；保留约 10% 重叠和原文位置，标题/查询指令计入模型输入限制。超长条款不能静默被模型截断。旧运行继续使用旧 chunker_version 和已有证据，不重写历史块 ID。

政策改版、未来生效与下线继续按原有规则：只选运行创建时已生效的最高版本；最高有效版本下线不自动回退旧版。新版本尚未建立向量索引时，使用该新版本的词法检索，不拿旧版本向量补位。

故障任务最多自动尝试 3 次，超时/临时服务错误退避重试；无效维度、非法输入直接失败。扫描 pending 记录补发，不能只依赖数据库提交后的单次队列发送。关闭/重启 worker 后不得留下永久 running 状态。

## 5. 一次检索如何执行

1. 从认证信息取得 tenant_id，模型不得指定或改写租户。
2. 获取本次运行的政策快照，确定允许的 policy_id、version、chunker_version 和 index_generation；快照同时固定未索引时的降级模式。
3. 按快照及已知订单状态过滤。没有订单信息时允许返回多种政策，但明确适用条件；不能擅自假定订单状态。
4. 在允许集合内并行计算现有词法排名与精确余弦排名，各取前 20 块。
5. 使用 RRF 融合，初始参数 k=60，按 chunk_id 去重，取前 5 块；并列按稳定 chunk_id 排序。第一版不引入额外 reranker，避免无法区分改进来源。
6. 以标题、版本、位置、原文及块 ID 返回；模型只能引用本轮已返回块。
7. 原始问题最多补查一次；补查沿用相同权限、版本、候选数和上下文预算。仍无依据时追问或转人工。

RRF 分数只是排序分数，不能显示成答案置信度。最低相关性阈值在开发集上校准并冻结；引用存在、原文匹配不代表语义支持正确，后者必须独立评测。

权限过滤必须先于召回和内容读取，不允许“全库检索后在前端隐藏”。向量查询失败时显式标记 `lexical_fallback` 并使用当前快照词法检索，不假装混合检索成功。

运行内先保持现有完整资料快照作为兼容边界；模型上下文仅传入 top-k 摘录。后续需要缩小数据库快照时再迁移为不可变版本引用，不在本轮同时重写恢复架构。

## 6. Agent、引用与审批

保留 `search_policy`、`get_order`、`draft_ticket` 工具。search_policy 新增结构化证据元数据，但保持旧 Mock 路径可运行。用户表达不完整时追问；材料有冲突时列出冲突条款，不自动选择更有利条款。

工单草稿关联订单快照和完整引用块。提交仍使用现有人工审批、版本和幂等约束。政策更新、撤回或订单变化时，在实际写入前重新验证并拒绝旧草稿；检索命中不能越过审批。

文档正文视为证据，不能改变系统规则、请求工具权限或指定其他租户。测试必须包含“忽略指令/批准退款”等嵌入文档的提示注入内容。

首轮预算：每任务最多 2 次政策检索，每次候选 20+20、返回最多 5 块；模型请求、时间与 Token 预算沿用执行器并单独记录 embedding 用量。上下文装配给输出和工具 Schema 留空间，超限时缩减证据并标记；不能无提示截断关键条款。

## 7. 本地模型与云端模型

新增明确的 provider 配置隔离：mock / deepseek / ollama；沿用统一消息与工具 Schema，在供应商适配器内转换协议。模型名称、版本、提示词哈希和采样参数进入运行记录。

DeepSeek 保持现有默认行为。本地 Qwen3 4B 的工具调用尚未通过验收，只作为实验选项。先验证单工具、参数错误纠正、多轮结果回传和停止条件，失败则显示“不满足工具调用验收”，不自动切到付费模型。

本地模型首轮按 4k 上下文设计短任务；embedding 独立 CPU。云端和本地对照需使用同一小上下文资料集，另列云端完整上下文实验，不将两者混为公平对照。模型费用按配置的价格和实际用量估算；本地记录延迟、内存/显存，不把零 API 账单称为零成本。

## 8. 工作台改动

沿用现有布局与配色，不新增蓝色主题，不另建平台。

- 订单与政策：索引状态、政策/索引版本、失败原因、按权限重试。
- 会话：真实阶段“查询订单 / 检索政策 / 生成草稿 / 等待审核”；取消后停止状态推进。
- 证据抽屉：正文、来源位置、版本、检索方式、引用关联；默认不显示内部向量。
- 审核区：政策已变更时说明失效原因并提供重新核对入口。
- 评测页：区分检索评测、工具运行器评测、端到端评测；支持查看失败样本和导出。

API 拟新增：GET 政策索引状态、POST 索引重试、GET 运行检索轨迹。索引重试限 admin/staff，轨迹必须校验租户与运行访问权。优先扩展现有 service 路由；具体路径在实施计划中与现有接口逐一对齐。

## 9. 评测设计与发布门槛

先冻结至少 36 例：18 开发、18 留出测试，覆盖直接规则、同义表达、多条款、无答案、未来版本/下线、租户越权与提示注入。相同问题的改写归入同一分组，避免跨集合泄漏。合成订单和政策必须标明，不冒充真实用户数据。标注正确条款集合、预期动作和不可接受行为；没有答案的问题不计入召回率分母。

离线检索比较：现有词法 / 向量 / 混合，固定同一资料、分块与查询。先独立对照分块改动，再对照检索算法，避免把多个变化归为向量收益。

| 指标 | 定义 / 门槛 |
|---|---|
| Recall@5 | 有答案任务中命中正确条款数量 / 应命中条款数量，逐题平均 |
| MRR@5 | 首条正确条款倒数排名均值，未命中为 0 |
| 过滤错误 | 跨租户、未来/撤回版本进入返回证据必须为 0 |
| 引用合法性 | 引用属于本轮已返回证据且可定位原文，集成测试必须全部通过 |
| 语义支持率 | 人工复核支持结论的引用数 / 已复核引用数，未复核不填分数 |
| 端到端完成率 | 完成预期业务动作且证据、权限、审批均正确的任务数 / 总任务数 |
| 性能 | 检索与全链路分别报告 p50/p95、模型请求、输入输出 Token、embedding 耗时 |

检索测试不调用生成模型。真实模型端到端实验显式启用，冻结后每题重复 3 次、保留所有失败与超时，不只选最好一次。先跑 6 例冒烟再扩大；人工评审与自动契约分开计分。

混合检索是否默认启用：留出集 Recall@5 不低于词法基线，至少改善一类同义/多条款样例，过滤错误为 0；未达到则保持词法默认并公开实验结果。不预写“提升 xx%”。性能门槛在首轮硬件基线后冻结，报告必须列硬件及并发数。

必须通过的工程场景：同一文档重复索引；索引中途退出；模型不可用降级；政策更新前后运行快照隔离；重复确认单工单；审批时政策撤回；viewer 越权；跨租户同 ID 查询；取消后迟到结果不得写回；模型伪造引用；文档提示注入。

## 11. 迁移、回滚与交付

新增迁移编号沿用项目现有版本体系，先备份数据，在 SQLite 和 PostgreSQL 分别测试新库、旧库与重复升级。不修改旧政策正文、运行结果或已确认工单。

`RETRIEVAL_MODE=lexical|hybrid` 默认 lexical，hybrid 验收后再切换。关闭 hybrid 能回到原检索；保留历史索引供旧记录查证。数据库扩展及向量存储后端不成为 Mock 演示的硬依赖。

交付包含：接口与架构说明、数据来源声明、安装及模型获取步骤、固定评测命令、原始结果、失败分析、2–3 分钟演示脚本。新增效果完成验收前不得写成简历已实现能力。GitHub 上传、额外模型下载和付费评测不属于本次写稿操作。

## 13. 自检与评审

已检查：区分已有与新增、标明本地模型失败边界、无预填效果数据；租户过滤先于召回；索引未就绪不回退旧政策；失败降级可见；审批仍需实时复核；不以检索分数冒充置信度。
