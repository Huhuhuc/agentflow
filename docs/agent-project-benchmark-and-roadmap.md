# AgentFlow 开源项目对标与正式项目路线

调研日期：2026-10-12。范围：官方 GitHub 仓库、官方文档和本地 AgentFlow 代码对照；未部署这些外部项目，未运行真实模型。本轮不修改应用逻辑。

## 结论与定位

当前项目是具备工具调用运行器、人工确认、运行恢复和离线评测的 Agent 工程原型。真实模式已有模型自主选择工具的接口；Mock 模式仍是确定性规则演示。暂不能据此声称具备真实用户任务成功率或生产部署可靠性。

建议收敛为「AgentFlow：企业售后工单 Agent」。目标用户为客服和售后运营；目标任务为查订单、核对适用规则、追问缺失资料、生成草稿、经人工确认提交工单、查询处理进度。保留工作流编辑器作为配套能力，把一个业务闭环作为主作品。

| 项目 | 类型与已公开的能力 | AgentFlow 应学习的部分 |
| --- | --- | --- |
| [Open SWE](https://github.com/langchain-ai/open-swe) | 编程 Agent 应用；调查代码、实施修改、验证并交付 PR，支持后续反馈及集成入口 | 清晰的业务产物、持久会话、工具执行边界、验证后交付；不照搬代码沙箱 |
| [Open Deep Research](https://github.com/langchain-ai/open_deep_research) | 研究 Agent 应用；可配置模型、搜索工具、研究流程及评测 | 输入→补齐资料→工具获取证据→产出成果→评估的完整流程 |
| [LangGraph](https://github.com/langchain-ai/langgraph) | Agent 编排基础设施 | 会话状态、检查点、中断恢复；它不是现成售后产品 |
| [Dify](https://github.com/langgenius/dify) | 应用开发平台；工作流、知识库、模型及工具接入、观测 | 配置与发布的完整链路、知识文档生命周期、可用的集成；不以复刻整个产品为目标 |

- [Dify README](https://github.com/langgenius/dify/blob/main/README.md)：知识处理、工作流、工具及观测。

## 本地代码的实际差距

| 维度 | 已有能力 | 尚缺什么 |
| --- | --- | --- |
| 模型执行 | business_agent.py 调用 real_turn，支持工具调用和限额 | 真实模型评测尚未进行；Mock 通过不能代表推理表现 |
| 数据 | 3个合成订单、2条政策，工具结果带证据 ID | 业务记录在 Python 常量中；无订单导入、检索文档入库和政策版本管理 |
| 会话 | 单次运行内多轮模型/工具交互、故障检查点 | 用户被要求补充信息后，缺少在同一会话补充并继续任务的接口和界面 |
| 人工介入 | 最终草稿确认、拒绝、取消 | 缺少编辑草稿后校验、补充资料、审批事件与执行结果关联 |
| 执行 | 租约、过期回收、旧执行器防写回 | business_api.py 仍使用 BackgroundTasks；Celery 的 worker.py 只执行工作流 |
| 对外工具 | 企业 Agent 工具读合成数据，确认写本地工单 | 无独立订单/工单服务适配器；engine.py HTTP节点返回 mock，通知节点仅生成结果对象 |
| 评测 | 24例分dev/test、自动契约检查、人工复核、CLI对比 | 规模小，开发/测试案例结构相近；缺少业务独立采样、数据库实验管理和真实模型结果 |
| 权限 | JWT、运行/工单租户过滤 | 页面自动登录固定演示账号；未形成完善的角色授权及业务数据权限边界 |
| 运维 | Compose、PostgreSQL/Redis配置、健康接口 | 没有本项目 .github CI目录；缺少数据库迁移与 PostgreSQL 并发验证 |

上述差距基于本次实际阅读的本地文件。此前71项后端测试通过是本地回归记录，不表示已经验证容器部署、PostgreSQL并发或真实模型效果。

## 下一阶段的优先级与验收标准

### 第一阶段：把单次演示改成可持续处理的业务任务

1. 新增 Conversation、Message、Task，将用户会话、目标任务和某次执行 Run 分开。支持 awaiting_input 状态及补充消息接口，保留已经确认的订单与证据。
2. 新增 Order、Policy、Ticket 的持久化数据和导入入口。政策记录版本、适用条件、启停/生效时间；订单归属租户。使用明确标注的合成或获授权数据。
3. 将 get_order/search_policy/draft_ticket 拆为工具模块，定义参数、返回值、权限、超时、读写类型和版本。领域规则由服务端校验，模型负责理解和选择工具。
4. 将工单确认扩展为“编辑草稿→校验→确认→提交结果”，提交记录 idempotency_key 和审计事件。业务数据发生变化时重新验证草稿。

验收场景：用户说“我要申请退款”→Agent追问订单号→用户回复“A102”→Agent沿用同一会话核对政策→生成草稿→用户修改说明后确认→得到一个可查询的工单；刷新页面后能继续查看；重复确认返回同一个工单；其他租户无法读取该订单。

这一阶段无须模型 API：用脚本化模型响应测试多轮状态和工具协议，并明确标注测试模式。

### 第二阶段：让证据来自可维护的文档

先支持 Markdown/TXT 政策导入，记录文件版本、分段、标题、原文位置。建立关键词/BM25基线；业务确有同义表达召回问题后，再加入本地向量或混合检索。无需为了贴 RAG 标签直接引入复杂检索组件。

检索同时过滤租户、政策有效期及适用条件；返回来源、段落、版本。没有足够依据时明确补充资料或转人工。

验收：修改或下线政策后，新任务使用新版本，旧任务仍能解释当时采用哪一版；过期文档不被当作有效依据；另建检索测试集，测目标段落是否进入前K条结果，而不是只查引用ID存在。

### 第三阶段：独立执行与可恢复的写入

企业 Agent 接入已有 Celery/Redis。API负责鉴权、创建任务和读取状态；worker执行模型/工具；PostgreSQL存储任务、检查点及执行事件。保留现有租约与防旧写入设计，并在 PostgreSQL 上验证竞争场景。

加入创建任务幂等键、队列并发上限、可操作的失败状态、结构化 ToolError。外部工单适配器可先连接本地独立服务；写入采用幂等请求或事务发件箱，明确请求可能重复，不把本地唯一约束说成对外 exactly-once。

验收：重启 API 不丢队列任务；结束 worker 后可恢复；同一提交重试不会新建多个任务或外部工单；队列拥塞时显示等待；取消不再提交新工具写入。

### 第四阶段：把评测变成可持续改进的入口

在服务端保存 Dataset、Case、Experiment、Score；记录代码版本、提示词版本、工具版本、知识版本、模型参数。页面创建实验、筛选错误类型、查看对照、记录人工评分，无需以手动导入文件作为唯一入口。

逐步采集更丰富的独立任务，覆盖不同表达、政策日期、缺失证据、服务超时、权限错误及重复提交。案例数量按覆盖需求增加，不能靠同句改写凑数。上线后将经过脱敏和审核的失败任务加入开发集，保留真正独立的测试集。

可先规范本地 trace，再选接 Langfuse；核心是 run→模型调用→工具/检索→结果之间能关联，且未知用量保持未知。

### 第五阶段：交付质量

增加 GitHub Actions：后端测试、前端类型/构建、数据库迁移和关键集成测试。提供一条命令启动的演示环境、示例数据、真实模式配置模板、3分钟演示脚本和故障恢复说明。

生产模式不自动使用演示账号或默认密码；按角色限制审批/管理权限；提供依赖就绪检查。对外发布之前补做目标部署环境的验证。

## 架构取舍

推荐保留 FastAPI、React、SQLAlchemy、PostgreSQL 和现有评测成果。会话状态复杂度上升后，可对比自写运行器与 LangGraph，不必为了框架名全量重写。选一个任务做适配实验，并用同一组测试比较中断恢复、可调试性及代码复杂度。

MCP是工具接入选项，不等于业务授权或幂等保障；多Agent应在任务确实可拆分且有实测收益后引入；向量库、Kubernetes和全自动写入均不属于当前必选项。

## 面试可验证的完成标准

- 陌生人按 README 能启动并跑完一个完整业务任务。
- 多轮追问、数据导入、人工编辑审批和实际持久化结果能现场展示。
- 能演示一次服务故障恢复、一次权限拒绝和一次重复请求去重。
- 能解释模型、确定性规则、检索和数据库各自负责什么。
- 有真实的实验记录及失败分析；暂未运行模型的部分明确说明。

优先顺序：会话与补充信息 → 业务数据与政策入库 → 工具与工单闭环 → 独立worker → 评测与交付。暂不配置API也能完成前面的工程建设，但最终验证Agent语义能力仍需要实际模型运行。
