# 企业服务 Agent：评测与可靠性

本次按已确认的两项范围改进：可重复评测，以及运行任务的取消、去重、崩溃恢复。不涉及游戏数据。

## 快速使用

1. 双击项目根目录 `evaluate-business.bat`，生成 Mock 开发集报告。
2. 启动 AgentFlow，进入默认的「企业服务 Agent」，滚动到「评测与人工复核」。
3. 导入 `backend/evaluation/reports/business-mock-dev.json`。展开案例，查看期望动作、实际动作、依据、工具调用及失败信息。
4. 依据每条样本的事实标准选择「正确 / 错误」，填写说明，点击「导出含复核记录的 JSON」。复核在浏览器内进行，刷新前需导出保存。JSON 可再次导入继续复核。

## 固定评测方法

`backend/evaluation/business_cases.json` 有 24 个合成业务案例，12 个开发样本、12 个测试样本，文本不重复。包括退款申请、人工审核、配送工单、订单缺失、规则缺失、明确否定建单、指令注入、多订单歧义及不适用规则。

开发集用于定位问题；修改提示词或执行逻辑后冻结版本，再运行测试集。不要反复用测试集调参，也不要改金标准来获得更高成绩。这是小规模功能评测，不能声称代表真实用户分布。

报告记录数据集 SHA-256、运行器代码 SHA-256、模型名、时间、分组、重复次数、逐轮轨迹和失败样本。预期动作与人工复核标准只供评分，不发送给模型。评测使用独立内存数据库，不会修改业务运行记录或自动确认工单。

自动指标包括运行完成率、动作正确率、工具契约正确率、引用 ID 正确率、综合契约通过率及 P50/P95 延迟（最近秩法）。工具检查包含订单参数与是否生成草稿；引用检查不能证明规则适用性和回答事实正确。全部人工复核完成后，界面导出的报告才计算事实正确率和端到端成功率，未完成时保持 null。

Mock 仅验证运行链路与规则基线。初次开发集运行的契约通过率为 9/12（75%），失败包括否定工单请求、多订单歧义和未签收订单套用签收后退款规则。后续改进了提示词、Mock策略与工具/回答校验，在未修改金标准的情况下达到12/12。原始报告另存 business-mock-dev-baseline.json，改进报告为 business-mock-dev-improved.json；均不能代表真实模型准确率。

## 真实模型评测

在 `backend/.env` 配置 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`（与现有真实执行共用配置）。没有密钥时明确报错，不回退 Mock。DeepSeek 具体配置与单样本检查见 [DeepSeek 接入说明](deepseek-setup.md)。

在 backend 目录执行：

```powershell
# 先用一个开发样本验证模型连接
.\.venv\Scripts\python.exe -m app.business_evaluation --mode openai --split dev --limit 1 --output evaluation/reports/business-real-smoke.json

# 冻结实现后运行测试集，每题重复三次（共36次 Agent 运行）
.\.venv\Scripts\python.exe -m app.business_evaluation --mode openai --split test --repeats 3 --output evaluation/reports/business-real-test.json
```

模型需要支持 Chat Completions 格式和 function calling。每次运行限制 6 轮、8 次工具调用、12000 Token 和累计已记录的120秒运行时间；最多5次重复实验。真实评测会消耗 API 额度，先检查单样本连接与开销。

费用由模型实际返回的 prompt/completion token 与手动提供的每百万 Token 单价估算；可追加 `--input-price 数值 --output-price 数值`。这两个价格应使用同一币种，按所选供应商实际报价填写。未提供价格、用量缺失、发生请求重试或执行失败时总费用保持 null，不能写成免费。缓存、供应商额外费用等可能导致账单不同，以供应商账单为准。

JSON 保留完整证据与轨迹；CSV 方便汇总；Markdown 列出指标和失败样本。文件中没有密钥，但会包含评测输入和模型输出。

比较不同提示词/模型版本时，追加 `--compare 旧报告路径.json`；要求数据集哈希、分组、重复次数和样本列表一致，输出指标差值和新增失败案例。Mock 与真实模型对照仅作为规则基线比较。

## 运行可靠性

- **原子领取**：任务必须由 pending 原子切换到 running 才能执行，重复调度同一运行 ID 只有一个执行器成功。
- **执行租约**：新建 `business_leases` 表，不改旧表。租约保存执行令牌、150秒到期时间和尝试次数。租约长于单次120秒运行预算，不跨网络请求持有数据库锁。
- **防止旧结果写回**：每次检查点、失败或完成写入都验证 running 状态、令牌与租约有效性。取消后的返回、租约过期的旧 worker 返回不能覆盖新状态。
- **自动回收**：服务启动后每5秒扫描过期 running，将任务重新排队，从最后一个已提交的工具轮次继续。最多两个恢复执行器并行；扫描独立于模型请求。支持回收升级前没有租约且已滞留150秒的企业任务，不处理其他 Agent。
- **有限重试**：一个运行 ID 最多领取三次，包含首次执行、人工重试和崩溃恢复，避免无限循环。超过后明确失败，需要新建任务。检查点中保留工具次数、消息、证据；已记录的 Token 和耗时跨恢复累计。
- **确认幂等**：确认使用状态条件更新与工单 run_id 唯一约束，同一运行并发确认只创建一个本地工单。

取消阻止后续状态写入，但不会强行中止已经发出的同步 HTTP 请求，供应商仍可能收费。硬崩溃发生在模型返回与检查点提交之间时，该轮可能重放，尚未提交的耗时与费用无法完整恢复；尝试次数上限限制重复执行。这里保证本地工单去重，不承诺模型请求 exactly-once。当前工具只读或生成草稿；未来接外部写入工具仍需对方的幂等键或事务发件箱。

## 验证

```powershell
# backend
.\.venv\Scripts\python.exe -m pytest -q
# frontend
npm.cmd run build
```

新增测试用真实 SQLite 文件和独立数据库会话验证并发领取、请求中途取消、两次同时确认、租约过期后的旧执行器写回、三次尝试上限。另有子进程 `os._exit(77)` 硬退出测试：第一轮工具结果已提交后进程退出，回收并继续，确认不会重复执行已提交的订单查询。

真实模型结果仍需配置密钥后运行并人工复核，不能把上述测试数量或 Mock 通过率写为模型准确率。并发测试目前覆盖 SQLite，本次未验证 PostgreSQL 部署。
